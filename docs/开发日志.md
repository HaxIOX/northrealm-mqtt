## 2026-08-11 排查 portable 启动慢/preload 失效，改用 ZIP 绿色版

**总结：portable 每次启动自解压 260MB 到 %TEMP%（约 1 分钟）并触发杀软扫描，是启动慢与 preload 注入失败的共同根因；实测打包版 preload 配置正常，遂将打包目标由 portable 改为 zip 绿色版（双击即开）。**

### 背景/现象
- 用户报告「桌面端未启用 MQTT TCP（preload 未生效）」。
- 用户报告 portable 打开慢、打不开。
- 现场诊断：portable 已运行（1 主进程 + 4 子进程），窗口从双击到出现约 59 秒；解压目录 260MB。

### 原因分析（标注依据等级：推算/文档/实测）
- 实测：主进程日志显示用户跑 portable（解压到 `%TEMP%\3Hhd50...`），`preloadExists:true`、webPreferences 正常、无 preload-error。
- 实测：用 Electron 加载 win-unpacked（与 portable v0.1.10 同批）的 preload + 打包 React 应用，结果 `SOURCE:'native'`、`mqtt.connect:function`、渲染层输出「✅ 使用Node原生MQTT，支持 mqtt:// 协议」——**preload 配置本身无问题**。
- 实测：portable exe 116MB，解压后 260MB（含 204MB electron 运行时 dll + node_modules 数千小文件），每次启动全量解压 + 杀软逐个扫描 → 启动约 1 分钟。
- 推算：preload 失效最可能为杀软在解压时拦截/延迟 mqtt 模块注入（渲染层 1 秒等待超时后降级 CDN）。
- 文档：electron-builder `zip` target 产出 win-unpacked 目录 zip，用户解压一次后双击即开，无每次解压开销。

### 改动
- `package.json`：`build.win.target` 由 `["nsis","portable"]` 改为 `["nsis","zip"]`；移除 `portable` 块。zip 产物采用 electron-builder 默认命名 `Northrealm-0.1.10-win.zip`。
- 说明：electron-builder 26 配置 schema **不支持顶层 `zip` 块**（首次构建报 unknown property 'zip'，已移除；zip target 无独立 artifactName 配置）。
- `.github/workflows/release.yml`：发布上传产物由 `release/*Portable*.exe` 改为 `release/*.zip`。

### 方案演进（含被否决的方案及原因）
- 保留 portable：它每次解压到 %TEMP% 是格式固有缺陷（非本次构建引入），无法缓存，否决。
- 杀软白名单：能缓解但无法根治且不可控，仅作辅助建议。
- 打包历史：v0.1.0（2025-12）起一直为 `nsis` 单 target；v0.1.10（2026-03）加入 `portable` 作为免安装方案；本次改为 `zip` 绿色版。

### 审查结论
- preload 配置经实测无问题；打包方案调整低风险，改动仅配置与 CI。
- **构建实测通过**（2026-08-11）：`npm run desktop:build` 生成 `release/Northrealm-0.1.10-win.zip`（145MB）+ Setup exe（104MB）；win-unpacked 为 asar 打包（app.asar 122MB）；真实运行 Northrealm.exe，渲染层输出「✅ 使用Node原生MQTT，支持 mqtt:// 协议」，TCP 能力正常。
- 体积说明：zip 145MB 大于旧 portable 116MB（electron 运行时 dll 占大头 ~200MB，asar 压缩 app 内容），后续可通过 firebase 按需加载进一步瘦身。

### 验证清单（如适用）
1. `npm run desktop:build`（需先关闭运行中的 Northrealm.exe）→ 确认 `release/Northrealm 0.1.10 x64.zip` 生成。
2. 解压 zip，双击 `Northrealm.exe`：应秒开（<2s）。
3. 用 mqtt:// 协议连接，确认无「桌面端未启用 MQTT TCP」提示。

## 2026-08-10 Windows 端 UI 优化（清理死代码 / 字体栈 / 窗口持久化 / asar / 系统主题跟随）

**总结：基于「简洁·美观·稳定·小巧」对 Windows 桌面端做五项低风险优化，不改组件结构与 MQTT 逻辑；除 asar 打包需构建实测外，其余均通过 lint/build 验证。**

### 背景/现象
- Windows 端 UI 全部堆在 `src/App.jsx`（3086 行），残留 Vite 模板死代码（`App.css`、`react.svg`）。
- 字体依赖 Tailwind 默认 `font-sans`，不同 Windows 机器渲染可能不一致。
- Electron 窗口无 bounds 持久化、无单实例锁，重启位置/大小丢失、可双开。
- 打包 `asar: false`，资源裸露、安装包偏大。
- 主题仅手动切换，不跟随系统偏好。

### 原因分析（标注依据等级：推算/文档/实测）
- 死代码：实测——`main.jsx` 仅 import `index.css`，`App.css`/`react.svg` 无任何引用。
- 字体：文档——Tailwind 3 preflight 的 `html` 字体与 `font-sans` 均取 `theme('fontFamily.sans')`，改配置即可全局生效。
- 窗口/单实例：文档——Electron `BrowserWindow.getBounds()` + `userData` 持久化，`requestSingleInstanceLock()` 防双开。
- asar：文档/推算——`asar: true` 后主进程 `loadFile`/preload `require` 走 asar 内读取（Electron 原生支持），mqtt.js 纯 JS 无需 asarUnpack；构建需用户实测确认。
- 主题跟随：文档——`matchMedia('(prefers-color-scheme: dark)')` 初始化 + `change` 事件监听。

### 改动
- A. 删除 `src/App.css`、`src/assets/react.svg`（无引用死代码）。
- B. `tailwind.config.js` 配置 `fontFamily.sans: ["Segoe UI","Microsoft YaHei","system-ui","-apple-system","sans-serif"]`，`html` 与所有 `font-sans` 统一字体栈。
- C. `electron/main.cjs`：新增单实例锁（`requestSingleInstanceLock` + `second-instance` focus）、窗口 bounds 保存到 `userData/window-state.json`（`close` 时写、启动恢复、屏幕外坐标丢弃、读写失败静默回退）。
- D. `package.json` build 配置 `asar: false → true`。
- E. `src/App.jsx`：无 `mqtt_theme` 记忆时按 `prefers-color-scheme` 初始化主题；监听系统主题 `change` 跟随，用户手动切换后（`themeUserOverride` ref）不再覆盖。

### 方案演进（含被否决的方案及原因）
- 字体栈方案：先在 `index.css` 的 `@layer base` 显式声明（PRD 初稿），后改为配置 `tailwind.config.js` 的 `fontFamily.sans`——避免 html 与 font-sans 双来源不一致，且符合 Tailwind 惯用法（否决前者）。
- 窗口恢复：简单保存 bounds vs 增加 `screen.getAllDisplays()` 屏幕外校验——为满足「稳定」理念（防窗口跑到屏幕外找不到），保留轻量校验（否决裸保存）。

### 审查结论
- 改动前已按 CLAUDE.md 执行三轮自检（静态/模拟运行/变体与失败注入），结论：可验证。
- lint：改动文件（main.cjs、tailwind.config.js、App.jsx）均 0 error；全库 1516 个 error 均为 android 构建产物等历史遗留，与本次无关。
- build：通过，字体栈已确认进入产物 CSS。

### 验证清单（如适用）
需用户在本机桌面环境执行：
1. `npm run desktop:build`：确认 `release/win-unpacked/resources/app.asar` 生成、`dist` 不再散落、安装包体积下降（asar 生效）。
2. 窗口持久化：调整窗口大小/位置 → 关闭 → 重开，尺寸与位置恢复。
3. 单实例：程序运行中再次启动，应 focus 原窗口而非新开。
4. 主题跟随：清空 localStorage 的 `mqtt_theme` → 切换系统主题，界面跟随；手动切换主题后系统切换不再覆盖。

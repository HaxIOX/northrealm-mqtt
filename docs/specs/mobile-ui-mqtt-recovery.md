# 移动端界面与 MQTT 恢复优化

## Goal

在保持桌面端主要操作习惯的前提下，使手机 App 的指令、消息和发布区域完整可用，并确保 App 从后台返回后能够可靠恢复 MQTT 连接与订阅。

## Users And Scenarios

- 用户在 360px 至 430px 宽度的 Android App 中查看消息、搜索、筛选并发送指令。
- 用户将 App 切换到后台后再次返回，应用能够恢复连接和已保存订阅。
- 用户恢复多个订阅时，只看到简洁、准确的汇总结果。

## Requirements

- 手机端默认显示消息与发布工作区，连接配置和订阅管理通过侧边抽屉访问。
- 桌面端保留固定侧栏和现有主要布局，不进行整体视觉改版。
- 快捷指令列表在手机端不得横向溢出；次要操作收入单个更多菜单。
- 发布工具栏允许响应式重排，Topic、QoS、Retain、定时和指令入口均可操作。
- 搜索、消息计数、筛选状态和日志操作合并为紧凑工具区。
- 消息列表减少无效留白，在不降低可读性的前提下增加同屏消息数量。
- App 回到前台时执行连接健康检查；连接失效时只创建一个恢复流程。
- 自动重连默认开启，用户手动断开后不得自动恢复。
- 恢复连接后按现有会话规则恢复已保存订阅，成功结果使用单条汇总日志。
- 不依赖当前仓库中缺失的 Android `MainActivity` 源码，优先使用 WebView 可用的页面生命周期事件。

## Not Included

- 不新增 MQTT 协议能力、后台常驻服务或 Android 前台服务。
- 不替换 React Context、Tailwind、MQTT.js 或现有持久化结构。
- 不改造云同步、桌面打包和 Electron 连接能力。
- 不进行品牌、配色或整体视觉风格重设计。

## Acceptance Criteria

- 360px、390px、430px 宽度下无页面级横向滚动，指令和发布操作完整可达。
- 手机端可打开和关闭连接配置抽屉，抽屉关闭后消息区占满可用宽度。
- 1366px 及以上桌面宽度继续显示固定侧栏，核心操作位置无明显回退。
- 纵向 800px 视口中，消息区域相较当前实现获得更多有效高度和更高同屏记录数。
- App 已连接时切到后台再返回，连接有效则不重建，连接失效则只发起一次重连。
- 用户主动断开后切换前后台，不会自动连接。
- 三个订阅恢复成功时只产生一条“已恢复 3 个订阅”类汇总日志。
- `npm.cmd run verify` 通过，并增加覆盖移动端布局和恢复状态机的定向测试。

## Open Questions

- 无。移动端采用侧边抽屉，恢复逻辑优先在 React/WebView 层实现。
